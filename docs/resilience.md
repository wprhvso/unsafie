# Отказоустойчивость и возобновление задач (Resilience & Recovery Engine)

## Обзор архитектуры

В `unsafie` реализована многоуровневая система отказоустойчивости (Fault Tolerance), позволяющая сервису выдерживать нештатные завершения процессов (`kill -9`, SIGKILL, OOM-killer ядра, внезапные перезагрузки контейнера или хоста) и автоматически продолжать выполнение всех незавершенных задач ровно с того места, на котором произошел сбой.

Система устраняет уязвимость монолитных in-memory корутин за счет пяти ключевых компонентов:
1. **Пошаговый Write-Ahead Checkpointing (WAL)**: сохранение состояния диалога (`messages`) до и после каждого вызова LLM и выполнения инструмента.
2. **Изолированный файловый спул (`BashSpool`)**: отвязка процессов bash от пайпов памяти Python с записью вывода и статуса завершения напрямую на диск.
3. **Супервизор восстановления (`RecoverySupervisor`)**: обнаружение зависших задач при старте ноды и периодический кластерный арбитраж с защитой от зацикливаний (Poison Pill).
4. **Идемпотентность Telegram**: детерминированные ключи идемпотентности для исключения дублей сообщений пользователю при повторах.
5. **Синхронизация шедулера и субагентов**: исключение параллельного повторного запуска задач по расписанию и надежная разблокировка субагентов после сбоев.

---

## 1. Пошаговый WAL (Turn Checkpoints)

Каждый агентский ход (`Turn`) сохраняет промежуточные снапшоты в таблицу `turn_checkpoints` и двухуровневый кэш (Redis L1 + PostgreSQL L2).

### Фазы шага (`CheckpointPhase`):
- `llm_query`: сохраняется массив сообщений `messages` перед отправкой сетевого запроса к Gemini API. Если сервис прерывается в этот момент, повторный запрос выполняется безопасно и идемпотентно.
- `tool_exec`: фиксируется полученный от модели ответ (`reply.as_message()`), код bash-блока и путь к рабочей директории спула до запуска команды.
- `tool_done`: фиксируется вывод команды, созданный блок и принятые из очереди сообщения (`queue.drain`).

### Формат хранения:
- Массив `messages` сжимается через `gzip` перед записью в PostgreSQL (экономия места до 80%).
- Для мгновенного доступа без дисковых задержек снапшот дублируется в Redis по ключу `checkpoint:<turn_id>` с TTL.
- При успешном завершении хода промежуточные шаги ротируются методом `prune()`.

## 2. Изолированный файловый спул (`BashSpool`)

Локальные команды bash запускаются через модуль `unsafie.agent.spool.BashSpool` в каталоге:
`/run/unsafie/spool/<turn_id>/step_<N>/` (fallback в `/tmp/unsafie-spool/...`)

### Структура спула:
- `run.sh` — исполняемый скрипт с прокинутым окружением (`PATH`, токены, git credentials).
- `stdout.log` — объединенный поток вывода, куда процесс пишет напрямую через дескриптор ОС. При гибели Python вывод не теряется.
- `meta.json` — PID, PGID процесса и timestamp старта.
- `exit_code` — атомарный файл с кодом возврата команды.

### Запуск и диагностика:
- Команда запускается в независимой группе процессов (`start_new_session=True` / `setsid`).
- Метод `probe()` возвращает текущий статус:
  - `RUNNING`: PID активен (`kill -0 pid == True`). Восстановленный сервис подключается к процессу и ожидает завершения.
  - `FINISHED`: найден файл `exit_code`. Считывается код и вывод, шаг завершается.
  - `DEAD`: PID мертв, файла `exit_code` нет (`interrupted = True`). Выставляется код выхода `137` и в контекст модели добавляется системное уведомление:
```
[System Notice: Command was interrupted by host restart or process kill. Partial output captured above. Please inspect workspace state (e.g. check created files, git status) and proceed.]
```
Модель видит факт обрыва и самостоятельно продолжает работу без зацикливания.

## 3. Супервизор восстановления (`RecoverySupervisor`)

Модуль `unsafie.agent.recovery.RecoverySupervisor` является фоновым демоном (`Loop`):

1. **Startup Sweep (`app.py` -> `lifespan`)**:
   При запуске сервиса (после миграций Alembic) вызывается `await recovery_supervisor.startup_sweep()`, который немедленно находит все ходы в статусе `RUNNING` от предыдущего падения и запускает `resume_turn()`.
2. **Кластерный опрос (`tick`)**:
   Каждые 15 секунд супервизор сканирует базу на наличие задач, чей `heartbeat_at` заглох более чем на 30 секунд (например, при падении соседней ноды).
3. **Защита от Poison Pill**:
   Если ход падает повторно и счетчик `Turn.recovery_attempts >= 3`, задача признается критически сбойной, помечается `FAILED`, и пользователю отправляется уведомление с кнопкой ручного повтора.
4. **Бесшовный `resume_turn`**:
   - Захватывает распределенный лок `chat_lock`.
   - Загружает последний чекпоинт.
   - Эмитит событие `turn.resumed` в Live Stream.
   - Включает Telegram typing.
   - Передает управление в `loop.run(..., initial_checkpoint=checkpoint)`.

## 4. Идемпотентность Telegram

Для предотвращения дублирования сообщений при повторе шага:
- Эндпоинты `/api/v1/chat/messages` и `/api/v1/chat/files` поддерживают `idempotency_key`.
- Если ключ не задан, он вычисляется детерминированно: `hash(turn_id + text + reply_to)`.
- Успешно отправленные сообщения сохраняются в Redis на 24 часа.
- При повторном запросе Telegram API не вызывается, а возвращаются сохраненные `message_ids`.

---

## 5. Задачи по расписанию и субагенты

- **`ScheduledTask`**: при срабатывании фиксируется `task.active_turn_id = turn.id`. В `ScheduleRepository.claim()` задача пропускается, пока связанный ход активен или восстанавливается, предотвращая параллельный повторный запуск.
- **`subagents`**: функция `wait_subagents()` периодически опрашивает PostgreSQL и слушает события Redis, предотвращая зависание родительского хода при потере in-memory событий.

## 6. Проверка сценариев отказа (Chaos Verification)

Для проверки устойчивости системы на сервере:
1. **Жесткий kill во время выполнения команды**:
```bash
# В момент выполнения агентом длительной команды:
kill -9 $(pgrep -f "unsafie")
systemctl restart unsafie # или перезапуск контейнера
```
*Результат*: unsafie поднимается, подхватывает ход в `startup_sweep`, считывает вывод из спула или переподключается к PID, и пользователь получает финальный ответ.

2. **Защита от дублей в чате**:
   При повторе шага, отправившего сообщение в Telegram, дубликаты отсутствуют.
